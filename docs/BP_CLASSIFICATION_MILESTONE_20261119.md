# BP版の分類評価マイルストーン

2026年11月19日（日本時間）

WindowsのBP画面で、CSVを選んで点検し、使う列を抽出してもう一度点検し、CPUで5モデルを比較して日本語の評価Excelを保存できるようになった。分割は行単位、顧客IDなどのグループ単位、日付順から選べる。元データを保持し、必要に応じて作業用Parquetを経由する。モデル選定と保留テストは共通のPython処理を使う。 [画面の起動と操作](DATA_AUDIT.md#データ点検の画面を使う)

この区切りでは、結果を読むときに必要な情報も一緒に保存できる。どの行を学習と評価に使ったか、何件を見逃したか、単純ルールでどこまで当たるかを、同じ評価の記録から確認できる。日付順では月別・ラベル別の内訳から、モデルと単純ルールの差が時期によってどう変わるかを調べられる。

## 実測で確認できたこと

- **Iranian Churn**では、7特徴量・3,150行を使った。行単位の保留テストでは630行中107行が学習側と同じ入力値を持っていた。同じ入力をまとめて分割すると、628行中0行になった。この例で使ったグループは特徴量の一致で定義しており、実際の顧客IDは使っていない。分割方法を変えると保留する行も変わる。 [グループ分割の記録](DATA_AUDIT.md#グループ単位の分割)
- **Bike Sharing**では、8・12・16・20時の2,913行から2012年8月7日〜12月31日の582行を保留した。貸出200件以上を「混雑」とし、カレンダー情報だけをモデルの入力にした。学習側の曜日・時間帯の多数決とモデルを、同じ保留行で比較した。 [データの作り方と検証結果](DATA_AUDIT.md#日付順の分割)

| Bike Sharingの予測方法 | 正解件数 | macro F1 | 「通常」109件のうち正しく検出 |
| --- | ---: | ---: | ---: |
| ランダムフォレスト | 410 | 0.638 | 80 |
| 曜日・時間帯の多数決 | 430 | 0.656 | 72 |
| 学習期間全体の多数決 | 473 | 0.448 | 0 |

この例では曜日・時間帯のルールが保留全体のmacro F1で最も高く、ランダムフォレストは「通常」の見逃しが最も少なかった。月別のmacro F1では8・9月にモデルが、10〜12月に曜日・時間帯のルールが上回った。これらは一つの保留期間の実測値で、差の不確かさは未評価。

## 検証と保存先

- Windows・Python 3.13.17でpytest全246件が通過。直近の実装で、曜日・時間帯のルールを元データから別計算し、保存した予測と照合した。月別の件数、日本語Excel、図付きExcelも確認した。マイルストーンの記録時に、行単位・グループ単位・日付順の3つの保存結果と図付きExcelを再検証した。
- ローカルの出力は `runs/bp-evaluation-ui-20261119`、`runs/bp-group-split-ui-20261119`、`runs/bp-bike-calendar-20261119` にある。別の環境では入力データと手順から再生成する。 [CLIと画面の再実行手順](DATA_AUDIT.md)
- 作業ブランチは `codex/bp-audit-preview`、起点は `5e7d1a3`（PR #1統合後）。このマイルストーンのGitへの保存・統合は、作業ブランチを対象とするPRとGit履歴で確認する。

## 次に再開するところ

1. **日付順の評価に合わせた誤差評価**。同じ保留行に対するモデルと単純ルールの差を、連続する観測日をまとめて再標本化する方法で検討する。観測日の抜けやブロックの長さによって結論が変わるかを、小規模な再現例で確認する。ラベルの確定が遅れる用途では、予測時点までに得た正解で学習する分割も検討する。
2. **学習曲線**。グループや日付順の分割を保ち、学習に使う量を変えたときの検証性能と計算負荷を調べる。その後、学習・選定からやり直したときの変動へ進む。
3. **BPの初回利用とDS向け手順**。BPでは「評価の分割方法を選ぶ」「単純ルールと比較する」「見逃しを読む」を初見でできるか確かめる。DSでは同じ実験をCLIで再生成する手順を整える。配布は別途検証する。 [ロードマップ](ROADMAP.md)

Annealing checkは引き続きDS向けの任意実行。QUBOとQuantum Annealingは将来の研究テーマとする。 [Annealing checkの方針](ROADMAP.md#annealing-check)
