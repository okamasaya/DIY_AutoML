前回は、元のCSVを保管しながら、点検後に圧縮した作業用データを作る流れを紹介しました。今回は、手元の16 GBのWindows PC（Core i5-14400）で、何行を扱うとどの工程にどれくらい時間がかかるかを測りました。

使ったのは、整数の特徴量と二値の正解ラベルを持つ、欠損のない模擬データです。元CSVは、表に示す特徴量に正解ラベルの1列を加えた構成です。各条件をCPUで3回ずつ順番に実行し、時間は中央値、メモリは3回のうち最も大きいPythonプロセスのピークワーキングセットを載せています。 [Microsoftのメモリ指標の定義](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters)

## 100万行を点検し、作業用ファイルを作る

CSVを読み、欠損・重複・正解ラベルの件数などをExcelに出しました。Parquetを作る場合は、元CSVを残し、点検に続けて数値型を付けた作業用ファイルを保存します。

| 元データ | 点検 | 点検＋Parquet |
| --- | ---: | ---: |
| 1万行・7特徴量 | 2.2秒 / 166 MiB | 2.3秒 / 177 MiB |
| 10万行・7特徴量 | 5.5秒 / 169 MiB | 7.4秒 / 185 MiB |
| 10万行・28特徴量 | 8.0秒 / 169 MiB | 15.6秒 / 187 MiB |
| 100万行・7特徴量 | 63.3秒 / 169 MiB | 91.1秒 / 186 MiB |

同じ10万行でも、特徴量を7列から28列にすると、点検と変換は7.4秒から15.6秒になりました。100万行・7特徴量の元CSVは36.2 MB、Parquetは18.9 MB（元の52.1%）でした。元の値の分布によって圧縮後のサイズは変わります。

100万行のParquetから、DuckDBで2条件を満たす先頭1万行をCSVに取り出す工程は2.3秒、ピーク186 MiBでした。この時間にはCLIの起動と抽出結果の保存が含まれます。元CSVから準備する場面では、表の点検・変換の時間もかかります。

## 抽出したデータで5モデルを比べる

抽出したデータから、学習と評価に使う1,000行・5,000行・1万行のCSVを用意しました。DIY AutoMLの `select` で、決定木・ランダムフォレスト・ロジスティック回帰・SVM・k近傍法を同じ5分割で比較しました。時間には、候補と分割を組み合わせた25回の学習、選んだモデルの再学習と保留テスト、1,000回のブートストラップによる評価区間、Excelへの保存を含めています。

| 学習・評価用データ | 時間 | ピークメモリ |
| --- | ---: | ---: |
| 1,000行・7特徴量 | 5.0秒 | 170 MiB |
| 5,000行・7特徴量 | 7.3秒 | 175 MiB |
| 1万行・7特徴量 | 10.4秒 | 195 MiB |
| 5,000行・28特徴量 | 11.6秒 | 184 MiB |

5,000行の2条件は同じ行を使い、特徴量の数だけを変えました。7特徴量の7.3秒に対し、28特徴量では11.6秒かかりました。学習と評価に使った最大規模は1万行・7特徴量です。

## 自分のデータで測るときに見るところ

今回の100万行では、元の表を一度点検して圧縮する工程と、用意した作業用ファイルから必要な行を取り出す工程で、待ち時間が大きく違いました。元表の更新頻度と抽出を繰り返す回数が分かれば、準備にかかる待ち時間を見積もれます。

今回の表のメモリはPythonプロセスの値です。実運用の負荷を見積もるときは、対象データの列構成・件数でかかる時間を測り、ほかのアプリも含めたメモリや一時ディスクの使用量も確認します。測定コードと各反復の結果はリポジトリの `experiments/tabular_scale_benchmark` にまとめました。 [DIY AutoMLのリポジトリ](https://github.com/okamasaya/DIY_AutoML)
